# E1：局部几何有改善，但发现截字反例，不能进入 OCR

**唯一选中且IoU≥0.5由E0 A的24/304提高到70/304，IoU≥0.7由5提高到69；但sample164明确截掉上部字符，仍通过七区检查。E1不能作为完整车牌裁剪器交给OCR或产品RTL。** 本轮证明局部文字行几何能改善粗框，同时找到了必须补足的完整性判据。

严格复用E0 A全部417个候选：44个原边界拒绝条目保留，373个有效粗框各精修一次。读取原development源图304次，全帧定位0、全帧Otsu分支0、模型前向0、训练0、84/112读取0。原画布、E0原结构和冻结源码均核对一致。没有根据结果修改参数、重跑局部精修或覆盖E0。

## 截字反例与完整性缺口

复查了70张选中裁剪缓存，以及原粗框/精修对照。`sample-164-inspection.png`显示：原粗框能看到字符上部，最终框只覆盖偏下的一段，再拉伸到224×64，上部笔画被截掉。其IoU为0.5083、GT面积裁失49.17%。局部阈值观测到的七组只有16…19像素高，将这些下部片段误当成完整字高，是这次错误几何的直接依据。

原七区检查会先清除上下5行、左右4列。sample164清边前有多个字符大小的组件直接穿过最终ROI上边界；清边后，六个字区都从第5行开始，却仍通过宽高、谷值和行一致性。这说明本轮实现的“搜索区域触边拒绝”没有覆盖“最终裁剪前的真实笔画截断”。需要补最终ROI完整性检查，不能只要求原尺寸组件未触碰粗搜索边界。

该帧GT校正区域没有形成七区，因此自动前景裁失诊断为**未知**，不是“没有截字”。另外69帧在这项掩码诊断中前景裁失均为0，但掩码不是人工笔画标注；联系图中未见其他同样明显的截断，也不能据此认证其全部完整。

所有选中框都未完全包住GT牌框；GT面积裁失P50/P95为8.16%/14.67%，多为文字附近比牌框更紧的几何，sample164是极端反例。保留这一事实，不能将GT边框不包含统一解释为无害裁边。

为了定位缺口，另外对70张**已有最终缓存**计算清边前诊断，没有再读取源图或运行精修：沿用同一Otsu，将高≥23、宽1…36且触碰224×64边界的组件标出。正极性标出17帧、负极性8帧，合计22帧，包括164。这只是事后诊断，边框、铆钉或反极性背景也可能被标出，**未把该规则回填成E1门控或新的成功结果**。记录在 `raw-border-diagnostic.json`；视觉结论独立写入 `visual-review.json`，原冻结帧记录不改写。

|---|---:|---:|

因此原先未细分的118个匹配候选失败，已确定为空区26、宽度60、高度32；不是局部Otsu单灰度。E1最终157个裁剪的正极性结构失败为宽度6、谷值4、高度1，其余146项通过；新的主要损失已前移到组件归组和唯一性，而非最后的七区检验。

## 歧义、退化与成熟实现的差异

34帧歧义全部来自**同一个粗框**，不是多块独立车牌。其候选的实际组件并集都不同，最小组件Jaccard为0.6，最小框间IoU为0.678。多数是大部分字符相同、某个碎片是否归入首末字不同。不能把它们当成完全重复框，或挑最长线、最高GT IoU的一项。sample18对照缓存展示了两条相近但不同的局部假设。

丢失的E0命中身份：21、52、59、78、112、188、227、243、263、292、293、349、437、438。其中227/349/438为歧义，其余11帧没有可用几何。已保留每个组件和每对锚的拒绝计数：

- sample21：一个宽166像素的连通组件包含框/粘连内容；可独立组成字符的组件不足七组。原粗框图像与组件记录共同支持“字符与框连接”这一路径，不能靠补首字解决。
- sample112：存在七个锚，但19个行假设都因最终余量超出已有搜索区域而拒绝；78、243、292也有这类失败。原框缺少足够观察余量时，不能把外推结果标为完整。
- sample293：首位相关组件触碰搜索左/下边界，且两条窄竖字组件填充率略高于本轮0.90筛选上限。该上限是E1适配，并非OpenALPR尺寸过滤的原规则；它会排除某些合法窄字，需作为规则缺陷保留，不能将全部失败归咎于画质。
- sample164：单个原尺寸阈值遗漏了字符上部，局部七组可以是真实笔画像素的**不完整部分**。原结构清边又掩盖了最终裁剪触边证据。

复读的 [OpenALPR字符分析](https://github.com/openalpr/openalpr/blob/master/src/openalpr/textdetection/characteranalysis.cpp) 在组件行估计前后还有阈值集合、外框掩码、孔洞关系及行间区域过滤；E1只采用单阈值和bbox/RLE归组，不能声称等价复现了成熟完整方案。[EasyPR局部搜索](https://github.com/liuruoze/EasyPR/blob/a0a9f3c3f612e7c8d9046bd9c5770249cfb86850/src/core/plate_locate.cpp) 也会处理局部边界，直接借用其默认裁边又会引入颜色依赖。下一步应围绕这些实际差异研究，而不是放松七区或倾斜门限。

建议主控下一轮先解决**完整性误接收**：保留最终裁剪清边前的笔画/组件边界证据，明确字符与框、铆钉及碎片的归属，再决定是否统一相近行假设。sample164必须成为拒绝验收例。仅解决局部精修仍不会恢复上游缺失64帧，需继续单列；本轮不新增全帧阈值实验或OCR预算。

## 资源模拟与复核

746个局部正反极性组件分区与独立OpenCV一致，活动标签在EOF归零。实际峰值为30条行游程、30活动槽、40保留组件、39碎片、55个锚组件对；没有溢出。合成测试另覆盖65碎片溢出、33帧几何溢出、重复精确四角、不同四角歧义、真实首位碎片合并、缺首字拒绝和平移不变。

独立Sutherland–Hodgman凸多边形裁剪复核157项精修IoU，最大误差7.39×10⁻⁷。373份原尺寸BGR与157份最终BGR缓存哈希全部一致。软件局部调用P50/P95/max约9.49/74.06/145.37ms（该统计含44个边界跳过项），不代表FPGA吞吐，也未做RTL映射。

产物在 `tmp/blue-plate-char-segment/edge-localization-e1/`：合同、身份、冻结SHA、304份逐帧记录、304份压缩裁剪缓存、`summary.json`、`audit.json`、边界诊断及四张检查图。源码只增加到 `tools/blue_plate/char_segment/`，验证文档只写当前子目录；E0、原模型、产品RTL、上板文件和README未改。

当前结论是“局部几何改善，同时发现完整性错误”，不是识别目标已完成。下一实验须保留该反例和全部退化身份，先解决错误裁剪再考虑进入OCR。
